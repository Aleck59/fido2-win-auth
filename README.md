# FIDO win auth

Вход в Windows 7–11 по аппаратному ключу **FIDO2** для **локальной** учётной
записи — без Entra ID и без домена.

Реализуется как **Credential Provider** (COM-DLL, которую загружает `LogonUI`).
На Windows 8+ провайдер встраивается в существующую плитку пользователя как
способ входа в «Параметрах входа» (значок рядом с PIN и паролем), а не отдельной
учётной записью. На Windows 7 — отдельной плиткой (там меню способов входа нет).

> **Статус: реализовано, нужна проверка на реальном железе.** Весь прикладной
> код написан (common, enroll, GUI, Credential Provider, установщик), кросс-сборка
> под MinGW проходит, криптографический слой покрыт тестами (round-trip под
> Wine). На живой Windows с аппаратным ключом связка ещё не обкатана — относитесь
> как к бете.
>
> ⚠️ **Сначала испытайте на виртуальной машине или запасном компьютере.** Всегда
> оставляйте второй способ входа (пароль администратора или второй ключ): ошибка
> в Credential Provider может лишить вас входа в систему.

## Как это работает

1. **Регистрация** (утилита `enroll`): на ключе создаётся credential с
   расширением `hmac-secret`. Пароль локальной учётки шифруется ключом,
   выведенным из `hmac-secret`, и запись кладётся в реестр под SID пользователя
   (ACL «только SYSTEM»). Сам пароль нигде не хранится в открытом виде.
2. **Вход**: Credential Provider получает от ключа `hmac-secret` (с PIN и
   касанием), расшифровывает пароль и отдаёт его Windows как обычный вход по
   паролю. Профиль, DPAPI и сетевой доступ продолжают работать.

   Обращение к ключу выполняется в `Connect()` на фоновом потоке, который
   LogonUI выделяет для этого сам, поэтому экран входа не подвисает на время
   ожидания касания и показывает ход операции («Коснитесь ключа...»).

Без физического ключа и его PIN зашифрованная запись бесполезна.

## Архитектура

| Слой | Назначение | Основа |
|------|-----------|--------|
| `src/common/token.*`  | работа с ключом: регистрация, получение `hmac-secret` | **libfido2** |
| `src/common/vault.*`  | шифрование/расшифровка пароля (HKDF-SHA256 + AES-256-GCM) | LibreSSL (в составе libfido2) |
| `src/common/store.*`  | запись/чтение записей в реестре по SID | Win32 |
| `src/provider/`       | COM-DLL Credential Provider (`ICredentialProviderCredential2`) | Win32/COM |
| `src/common/enrollment.*` | последовательность регистрации/проверки/удаления | — |
| `src/enroll/`         | консольная утилита регистрации | — |
| `src/gui/`            | окно регистрации (диалоги Win32) | comctl32 |
| `installer/`          | установщик NSIS | NSIS |

Вся работа с протоколом ключа (CTAPHID, CTAP2, PIN-протокол, `hmac-secret`)
делегирована проверенной библиотеке **libfido2** (Yubico), vendored в
`third_party/libfido2/` (версия 1.15.0, лицензия BSD-2-Clause).

## Сборка (кросс-компиляция под Windows из Linux)

Инструменты: `g++-mingw-w64-x86-64`, `nsis`, `wine64` (для тестов).

```
make            # DLL провайдера, enroll.exe, fido2gui.exe и тест (в build/)
make test       # round-trip тесты шифрования под Wine
make dist       # сложить бинарники и runtime-DLL в dist/
make installer  # собрать dist/fido2-win-auth-setup.exe (NSIS)
make clean
```

Проверено, что MinGW линкуется с MSVC-сборкой libfido2 и код работает под Wine
(C-ABI совместим). Рантайм C++/GCC линкуется статически, поэтому из зависимостей
нужны только четыре DLL libfido2 (кладутся рядом с провайдером установщиком).

## Использование

1. **Установка.** Запустите `fido2-win-auth-setup.exe` от имени администратора.
   Он кладёт провайдер, `fido2gui.exe` и `enroll.exe` в
   `Program Files\fido2-win-auth\`, регистрирует Credential Provider
   (`regsvr32`) и добавляет ярлык «Регистрация ключа FIDO2» в меню Пуск.
   Если регистрация отказывает в ключе, посмотрите, что он умеет: верхняя
   таблица в окне или `enroll --keys` в консоли. Прав администратора для этого
   не нужно.

2. **Задайте PIN ключа**, если он ещё не задан (Параметры Windows → «Ключ
   безопасности», или `ykman fido access change-pin`). Без PIN регистрация
   откажет — фактор PIN обязателен.
3. **Регистрация.** Проще всего — через окно: «FIDO win auth» в меню Пуск
   (`fido2gui.exe`). Права администратора оно запрашивает само.

   Сверху — таблица подключённых ключей: название, тип (FIDO2 или U2F),
   служебные данные (версии CTAP, наличие `hmac-secret`, состояние PIN) и
   флажок «зарегистрирован в этой программе». Флажок только показывает
   состояние, менять его нельзя. Ответ на вопрос «зарегистрирован ли этот
   ключ» выясняется ассерцией с выключенным признаком присутствия — без
   касания и без PIN. Некоторые ключи такой запрос не поддерживают; тогда в
   служебных данных пишется «регистрацию проверить не удалось», а флажок
   остаётся снятым — это не то же самое, что «не зарегистрирован».

   Снизу — таблица учётных записей с регистрацией.

   То же самое в консоли администратора:
   ```
   enroll                 # текущий пользователь
   enroll --account Имя   # другая локальная учётка
   enroll --list          # показать зарегистрированные
   enroll --keys          # что умеют вставленные ключи
   enroll --u2f           # регистрация ключа U2F (СЛАБЕЕ, см. «Два режима»)
   enroll --test Имя      # проверить, что вход сработает
   enroll --remove Имя    # убрать регистрацию
   ```
   Оба инструмента спросят PIN ключа и пароль Windows, затем потребуется трижды
   коснуться ключа: создание credential, получение `hmac-secret` и контрольная
   расшифровка перед записью. Если контрольная расшифровка не сойдётся, запись
   не сохраняется — неработающая регистрация не попадёт в реестр. Пароль в
   открытом виде нигде не сохраняется.

   Перед регистрацией пароль проверяется через `LogonUser`: опечатка в пароле
   иначе обнаружилась бы только на экране входа, где разбираться куда труднее.
4. **Вход.** На экране входа/блокировки появится способ «Вход по ключу FIDO2».
   Введите PIN ключа, коснитесь его — пароль расшифруется и уйдёт в Windows.

### Детали реализации

| Компонент | Файлы |
|-----------|-------|

| DPAPI (машинная область, только режим U2F) | `src/common/dpapi.*` |
| Открытие записи ключом (общее для входа и проверки) | `src/common/unlock.*` |
| Работа с ключом (libfido2) | `src/common/token.*` |
| Реестр по SID (ACL SYSTEM+Admins) | `src/common/store.*` |
| Credential Provider (COM, `ICredentialProviderCredential2` + `IConnectableCredentialProviderCredential`) | `src/provider/` |
| Иконка плитки и картинка в окне (генерируются) | `tools/make_tile.py` |
| Значок приложения (генерируется) | `tools/make_icon.py` → `src/gui/app.ico` |
| Имя и издатель для всех ресурсов | `src/common/product.h` |
| Логика регистрации (общая для окна и консоли) | `src/common/enrollment.*` |
| Окно регистрации | `src/gui/` |
| Консольная утилита | `src/enroll/` |
| Тесты | `tests/test_vault.cpp` |
| Установщик | `installer/installer.nsi` |

Запись в реестре: `HKLM\SOFTWARE\fido2-win-auth\vaults\<SID>` (REG_BINARY), DACL
только для `SYSTEM` и `Administrators`. Формат записи: `F2V1 | credId | salt(32)
| nonce(12) | ciphertext+tag`. Ключ AES = `HKDF-SHA256(hmac-secret, salt,
"fido2-win-auth vault v1")`, AAD привязывает шифртекст к `credId+salt`.

### Известные ограничения

- RDP не поддерживается (ключ на клиенте, а не на хосте сессии).
- Ключи, умеющие только U2F (CTAP1), поддерживаются **отдельным режимом и
  существенно слабее** — см. «Два режима» ниже. «U2F-ключ» при этом часто просто
  надпись на корпусе: проверьте через `enroll --keys`, прежде чем выбирать
  слабый режим.

## Ключи без кнопки

У части ключей кнопки нет, и подтверждение присутствия они выдают
**в момент подключения**, на несколько секунд. Если такой ключ уже вставлен,
регистрация в него упрётся: ключ будет отвечать «условия не выполнены», пока
не истечёт таймаут.

Поэтому операция с ключом вынесена в отдельное окно, которое **ждёт появления
ключа** и запускается ровно тогда, когда он подключён. Это работает для обоих
видов ключей: с кнопкой — вставили и коснулись, без кнопки — просто вставили.
Если ключ уже вставлен, окно предложит извлечь его и вставить заново; для
ключей с кнопкой есть и кнопка «Использовать вставленный ключ».

Отсутствие ключа при этом не считается ошибкой — окно просто продолжает ждать.
Если попытка не удалась (например, окно подтверждения на ключе успело
закрыться), достаточно вставить ключ ещё раз: окно пробует снова.

**Регистрация требует двух подтверждений** — создание credential и контрольная
расшифровка перед сохранением. Второе у ключа без кнопки взять неоткуда:
подтверждение, выданное при подключении, уже израсходовано. Поэтому перед
контрольной проверкой окно просит вставить ключ ещё раз и продолжает с того же
места — регистрация не начинается заново. В консоли то же самое: `enroll`
попросит перевтыкнуть ключ и нажать Enter.

**На экране входа** действует то же правило. Провайдер сначала быстро
опрашивает уже подключённые ключи (около 2,5 секунды — столько нужно ключу,
который уже готов ответить), и если никто не отвечает, просит вставить ключ и
запускает проверку в момент подключения. Ожидание длится до двух минут и
прерывается отменой входа. Раньше провайдер делал один проход по вставленным
ключам и молча ждал полного таймаута, из-за чего вход по U2F выглядел
зависшим и не реагировал на перевтыкание.

## Вход по подключению ключа

Для записей **U2F** вставленный ключ входит в систему сам — выбирать способ
входа не нужно. Провайдер следит за появлением ключа на экране входа или
блокировки, просит Windows переопросить способы входа и назначает свою плитку
с автоматическим входом.

Условия, при которых это срабатывает:

- запись в режиме **U2F** (в ней нечего вводить; записи FIDO2 требуют PIN, для
  них плитка просто выбирается, но вход не начинается);
- зарегистрирована **ровно одна** учётная запись. Какому пользователю
  принадлежит вставленный ключ, без обращения к ключу не узнать, а обращение
  тратит те самые секунды, которых у ключа без кнопки нет. При нескольких
  записях выбор остаётся за пользователем;
- ключ именно **подключают**. Уже вставленный при появлении экрана входа ключ
  ничего не запускает: первые пару секунд провайдер только запоминает, что уже
  подключено, иначе блокировка экрана тут же разблокировалась бы обратно.

Отключается одной командой:

```powershell
enroll --autologon off
```

> **Чем вы за это платите.** Это убирает нажатие, а не фактор: запись U2F и так
> открывается одним лишь ключом, без PIN. Но означает это буквально следующее:
> заблокированный компьютер без присмотра открывается в тот момент, когда в
> него вставят этот ключ. Если такое неприемлемо — выключите настройку выше или
> пользуйтесь режимом FIDO2, где требуется PIN.
>
> Ещё одно следствие: если вставить ключ, когда вы набираете пароль на обычной
> плитке, экран переключится на вход по ключу.

Экран входа при этом остаётся обычным: плитка ключа не выбрана и ничего не
занимает, способ входа и пользователя можно менять как всегда. Выбор плитки
ключа сам по себе вход не начинает — для этого есть кнопка. Автоматический
вход, если он не удался, молча уступает экран обратно, а не держит его
ожиданием.

## Если вход по ключу не работает

Провайдер работает внутри LogonUI от имени SYSTEM: ни консоли, ни окна, а
каждая попытка стоит перезагрузки. Поэтому у него есть журнал.

```powershell
enroll --debug on     # от имени администратора
# заблокируйте экран (Win+L), попробуйте войти
notepad C:\ProgramData\fido2-win-auth\provider.log
enroll --debug off
```

В журнал попадают только пройденные шаги и те же сообщения, что показывает
плитка: сколько ключей найдено, чем закончилась попытка, дошло ли дело до
передачи учётных данных в LSA. Пароль, PIN и материал ключа не записываются
никогда.

Пустой журнал при попытке входа означает, что `Connect()` не вызывался — то
есть плитка не запустила операцию, и проблема в интерфейсе плитки, а не в
работе с ключом.

## Два режима

| | FIDO2 (по умолчанию) | U2F |
|---|---|---|
| Протокол | CTAP2 | CTAP1 |
| Чем защищён пароль | ключом, выведенным из `hmac-secret` токена | ключом, который лежит на этом компьютере (DPAPI) |
| Роль токена | **держит секрет** | подтверждает присутствие подписью |
| PIN | обязателен | отсутствует в протоколе |
| Касаний при регистрации | 3 | 2 |
| Админ/SYSTEM может достать пароль без токена | **нет** | **да** |

### Почему U2F слабее

В CTAP1 нет механизма расширений — значит, нет и `hmac-secret`. Единственное,
что умеет U2F-ключ, это подписать challenge, и подпись каждый раз новая.
Воспроизводимого секрета, из которого можно вывести ключ шифрования, взять
неоткуда.

Поэтому в режиме U2F ключ шифрования генерируется случайно и хранится **на этом
компьютере**, защищённый DPAPI в машинной области. Подпись токена проверяется
по сохранённому открытому ключу и решает, прочитает ли программа этот ключ
шифрования. Разница принципиальная:

- **FIDO2:** без физического токена пароль недоступен арифметически.
- **U2F:** тот, кто получил SYSTEM или права администратора на этой машине,
  вызывает `CryptUnprotectData` ровно так же, как это делает провайдер, и
  расшифровывает пароль, вообще не трогая токен.

То есть в режиме U2F токен перестаёт быть замком и становится проверкой в коде.
Это осознанный размен ради работы со старыми ключами, и обе утилиты требуют
явного подтверждения, прежде чем его применить.

Что в режиме U2F всё же делается:

- Подпись проверяется по открытому ключу, сохранённому при регистрации, —
  чужой ключ не подойдёт.
- Счётчик подписей обязан расти; откат счётчика отвергается как признак
  клонированного ключа. Ключи, которые счётчик не ведут и всегда возвращают
  ноль, CTAP1 допускает, и такой случай ошибкой не считается.
- DPAPI-блоб привязан к `keyHandle` и открытому ключу записи, а открытый ключ
  входит в AAD шифротекста — переставить блоб или ключ в другую запись нельзя.

### Как выбрать

В окне — флажок «Режим U2F» в диалоге регистрации (с предупреждением), в
консоли — `enroll --u2f` (требует ввести `u2f` для подтверждения). Режим виден
в колонке «Режим» главного окна и в `enroll --list`.

## Безопасность и ограничения

- Требуется PIN ключа (user verification), иначе украденный ключ сразу даёт вход.
- Обязательно оставьте запасной путь входа (второй ключ / админ-учётка): сбой
  Credential Provider не должен запирать систему.
- RDP не поддерживается (ключ находится на клиенте, не на хосте сессии).
- Администратор машины всё равно может сбросить пароль штатными средствами —
  это не обход прав администратора, а добавление фактора для входа.
